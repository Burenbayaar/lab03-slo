## SLO

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл | k6 threshold (`slo-test.js`) |
|---|---|---|---|---|
| Performance | `/cart/add` latency | p95 < 10 ms | 20 VU тогтмол, 1 мин | `'http_req_duration{name:cart}': ['p(95)<10']` |
| Reliability | `/pay` error rate | < 8% | 20 VU, 1 мин | `'http_req_failed{name:pay}': ['rate<0.08']` |
| Availability | бүх хүсэлтийн амжилтын хувь (checks) | > 90% | 20 VU, 2 мин, 10 s зогсолт орсон | `'checks': ['rate>0.90']` |
| Нэмэлт (report) | `/report` latency | p95 < 450 ms | 20 VU, 1 мин | `'http_req_duration{name:report}': ['p(95)<450']` |

**Босго сонгосон үндэслэл:**
- **10 ms:** калибровкийн p95 = 1.53 ms; зааврын жишээ 200 ms нь localhost дээр ямар ч удаашралыг барихгүй, 10 ms нь ~6.5 дахин нөөцтэй боловч гүйцэтгэл 6+ дахин муудвал барина.
- **8%:** серверт 5% алдаа суулгасан (калибровк 4.63%); минутад ≈930 төлбөрийн хүсэлтэд санамсаргүй хэлбэлзэл ±0.7% орчим тул 8% нь хэвийн үед давагдахгүй, харин алдааны түвшин 1.5 дахин өсвөл барина.
- **90%:** хэвийн үед check-ийн амжилт 98.45% — `/pay`-ийн 5% алдаа ганцаараа ≈1.7%-ийг "иддэг"; 90% нь үлдсэнийг богино зогсолтод зориулсан нөөц.
- **450 ms:** `/report` онолоор 400 ms-ээс удаан хариулахгүй (калибровк p95 = 392.04 ms, max 400.52 ms); 50 ms нь сүлжээ ба event loop-ийн нөөц.

**Error budget (цагаар):** 2 минутын цонхонд 90% availability → эвдрэх эрх = 120 s × 10% = **12 секунд**. Хүсэлтээр тооцсон budget-ийг chaos туршилтын хэсэгт харьцуулна.

### FAIL — `slo-test-fail.js` (зориуд эвдсэн, `/report` p95 < 100 ms)

[`results/fail.txt`](results/fail.txt): `✗ 'p(95)<100' p(95)=387.55ms` — `/report` серверт 200–400 ms хүлээлт суулгасан тул
100 ms-ээс хурдан хэзээ ч хариулахгүй, ямар ч машин дээр найдвартай FAIL болно. Бусад гурван threshold PASS хэвээр:
`/cart/add` p95 = 1.14 ms, `/pay` error rate = 5.34%, checks = 98.21%. k6 мэдэгдэл:
`thresholds on metrics 'http_req_duration{name:report}' have been crossed`, **exit code = 99** (`exit=99` мөр файлд бий).
CI pipeline яг энэ 0-ээс ялгаатай exit code-оор build-ийг зогсоодог (quality gate).
Зааврын `echo "exit=$?"` нь `| tee`-ийн дараа tee-гийн exit code-ийг (0) хэвлэдэг тул k6-ийн жинхэнэ кодыг
`${PIPESTATUS[0]}`-ээр авсан.

`/cart/add`-ыг p(95)<50 болгосон ч localhost дээр PASS хэвээр үлдэх байсан — бодит p95 ≈ 1–1.5 ms тул 50 ms нь
хэт сул; threshold зөвхөн хэмжсэн утгатай ойр байж л "ажил хийдэг".

## Алхам 5: Мини chaos — availability сценариог бодитоор турших

Серверийг гараар Ctrl+C хийх нь хоёр terminal-ын хооронд цаг тааруулахад төвөгтэй байсан тул (эхний хоёр оролдлогод
сервер зогсоогүй) зогсолтыг скриптээр автоматжуулсан: 2 минутын `slo-test.js` (`-e DURATION=2m`) ажиллаж байхад
40 дахь секундэд серверийн процесс руу `SIGINT` (Ctrl+C-тэй ижил дохио) илгээж, 10 s хүлээгээд `node server.js`-ийг
дахин асаасан. Зэрэгцээ "probe" 0.5 s тутам `/cart/add`-ийг шалгаж, цаг ба HTTP кодыг бүртгэсэн.

| Хэмжүүр | Утга | Файл |
|---|---|---|
| Зогсолт | 14:42:10 → 14:42:20 (10 s) | [`chaos-events.txt`](results/chaos-events.txt) |
| Сэргэх хугацаа | эхний алдаа 14:42:10.570 → сэргэсний дараах эхний 200 14:42:20.413 = **9.84 s** (SLO ≤ 15 s ✓) | [`chaos-probe.txt`](results/chaos-probe.txt) |
| Нийт хүсэлт | 5709 (47.06 хүсэлт/с) | [`chaos.txt`](results/chaos.txt) |
| Амжилттай / алдаатай | 4994 / 715 | [`chaos.txt`](results/chaos.txt) |
| **Бодит availability (хүсэлтээр)** | 4994 / 5709 = **87.47%** → `✗ 'rate>0.90'` **FAIL** | [`chaos.txt`](results/chaos.txt) |
| Reliability (`/pay` error rate) | **15.86%** → `✗ 'rate<0.08'` **FAIL** | [`chaos.txt`](results/chaos.txt) |
| Performance / report | `/cart/add` p95 = 1.53 ms ✓, `/report` p95 = 389.24 ms ✓ | [`chaos.txt`](results/chaos.txt) |
| k6 exit code | 99 | [`chaos.txt`](results/chaos.txt) |

**Error budget — цагаар ба хүсэлтээр яагаад зөрөв.** Цагаар: 2 минутын 10% = 12 s; 10 s зогсолт үүнд багтах ёстой
байсан. Хүсэлтээр: 5709 хүсэлтийн 10% = **571** алдаа зөвшөөрөгдөнө, бодитоор **715** алдаа гарсан — budget
144 хүсэлтээр хэтэрсэн. Шалтгаан: (1) k6-ийн `checks` нь цагийн биш хүсэлтийн хувь; зогсолтын үед хүсэлт бүр
холболтын алдаагаар агшин зуур буцаж, `/report`-ын 200–400 ms хүлээлт алга болдог тул нэг давталт ≈1.3 s-ээс ≈1 s
болж, 20 VU × 3 хүсэлт ≈ **60 алдаатай хүсэлт/с** үүссэн (хэвийн үед ≈46 хүсэлт/с) — зогсолтын нэг секунд хэвийн
секундээс ≈30% илүү хүсэлт "иддэг"; 10 s × ≈60 ≈ 600 алдаа. (2) `/pay`-ийн суулгасан 5% алдаа (≈1.7% буюу ≈100 хүсэлт)
хэвийн үед ч budget-ийн нэг хэсгийг эзэлдэг тул зогсолтод үлдэх бодит нөөц 12 s биш ≈10 s орчим байсан.
Иймд 90%-ийн SLO нь 10 s зогсолттой хамт хэт өөдрөг байсан: энэ хэмжээний зогсолтыг багтаахын тулд SLO-г ≈85%
болгох, эсвэл зогсолтыг ≈7 s-ээс богино байлгах (жишээ нь процессыг автоматаар дахин асаадаг supervisor) хэрэгтэй.

**Нэг эвдрэл хоёр SLO-г зөрчсөн.** Сервер унасан үед `/pay`-ийн хүсэлт бүр унадаг тул reliability SLI (15.86%) мөн
availability-тэй хамт FAIL болсон. Хоёрыг тусгаарлахын тулд reliability SLI-д зөвхөн сервер **хариулсан** хүсэлтийн
5xx-ийг (жишээ нь `status: 500`-аар шүүсэн rate) тоолж, холболтын алдааг (status 0) зөвхөн availability-д тооцох нь зөв.

## Дүгнэлт

Сценарио → SLO → threshold шилжилтийн хамгийн хэцүү алхам нь босгын тоог сонгох байсан: зааврын жишээ 200 ms-ийг шууд
авбал localhost дээр 1.5 ms-д хариулдаг `/cart/add`-д ямар ч утгагүй, сул шалгуур болох байсан тул эхлээд калибровк хийж
бодит тоогоо харсны дараа босгоо тогтоосон. Хоёр дахь хэцүү зүйл нь 6 хэсэгтэй сценариогийн "Орчны төлөв" ба "Хэмжүүр"-ийг
тодорхой, хэмжиж болох (20 VU, ≈15 хүсэлт/с, p95, цонх) хэлбэрт оруулах байсан — "хурдан", "найдвартай" гэх мэт үгсийг
k6 шалгаж чадахгүй. Хэвийн ачаалалд дөрвөн SLO бүгд PASS гарсан (`results/pass.txt`), зориуд хатуу болгосон `/report`
threshold FAIL болж exit code 99 буцаасан нь CI-ийн quality gate хэрхэн ажилладгийг харуулсан. Chaos туршилт availability
